# HE Clinician Dashboard

[![Binder](https://mybinder.org/badge_logo.svg)](https://mybinder.org/v2/gh/dicristea/ehr-wearable-he-dashboard/main?urlpath=lab/tree/notebooks) · License: [BSD-3-Clause](LICENSE)

A clinician-facing dashboard for a hepatic encephalopathy (HE) study in which patients with cirrhosis wear an Oura ring. Built at Cornell Tech with [JupyterHealth](https://jupyterhealth.org).

> **Everything public here runs on synthetic data.** The patients (`DEMO-01` … `DEMO-24`) are generated by code. Patterns you see come from the generator's settings, not from real patients ([why](docs/synthetic-data.md)). The study data is never in this repository.

## What it does

Each patient's ring produces a daily export. The dashboard turns it into views a clinician can read in a few minutes: who looks worse than usual this week, what one patient's rest and activity look like over time, and how groups of patients compare. It was designed with the study's clinician, a hepatologist at Weill Cornell Medicine, and shows only what the study data actually contains (no sleep stages, no labs, no event dates).

| Tab | What you can do |
|---|---|
| **Patients** | Filter and sort the patient list (HE status, Child-Pugh, decompensation, age, MELD, data quality…). *Needs attention* flags patients whose last 7 days are worse than their own usual range. Click a patient for their profile: rest, regularity, HRV, heart rate, steps and SpO₂ against their own baseline, plus 24-hour activity patterns. |
| **Cohort** | Compare groups (e.g. decompensated vs. compensated) on any measure: weekly trajectories, one dot per patient, and a Mann-Whitney test. **Export** a PDF report or a ready-to-run notebook for the selected patients. |
| **Notebooks** | The exploratory analyses behind the dashboard. In the demo: view them read-only, or run them in JupyterLite or on Binder. Locally: open them in your own JupyterLab. |
| **EHR launch** | A minimal SMART on FHIR launch: an EHR such as Medplum opens the dashboard on the patient in its chart, matched by MRN. *Simulate launch* tries it without an EHR. |

It's a slimmed-down companion to the research prototype [oura-clinical-workbench](https://github.com/dicristea/oura-clinical-workbench), which keeps the ML lab, SHAP and AI assistant.

## Quickstart

Needs Python 3 and Git (tested with Python 3.13 on macOS). No study data and no R needed.

```bash
git clone https://github.com/dicristea/ehr-wearable-he-dashboard.git && cd ehr-wearable-he-dashboard
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/generate_synthetic_data.py
HE_DATA_SOURCE=synthetic python app.py
```

Open <http://127.0.0.1:5050>. You should see 24 synthetic patients and an amber "synthetic demo data" banner. Stop with Ctrl+C.

- **Windows:** activate with `.venv\Scripts\activate` and use `set HE_DATA_SOURCE=synthetic` (cmd) or `$env:HE_DATA_SOURCE="synthetic"` (PowerShell). Not yet tested on Windows.
- **A different cohort:** `python scripts/generate_synthetic_data.py --participants 40 --seed 3` (all options in [docs/synthetic-data.md](docs/synthetic-data.md)).
- **The public demo locally:** `HE_PUBLIC_DEMO=1 python app.py`.

## Notebooks

| Notebook | What it does |
|---|---|
| `notebooks/deid_oura_data_exploration.py` | A beginner-friendly tour of the dataset: who is in it, how complete it is, the sleep proxies, and what exists compared with the research workbench. |
| `notebooks/he_trajectories_phenotypes.py` | Group trajectories over the study, individual phenotypes (clustering), and why before/after-event analysis needs an event table. |

They are stored as [jupytext](https://jupytext.readthedocs.io) `.py` files with no outputs; `.ipynb` copies are git-ignored because outputs can contain data. To run them locally:

```bash
jupytext --to ipynb notebooks/*.py      # make runnable copies
HE_DATA_SOURCE=synthetic jupyter lab    # start from the repo folder
```

`HE_DATA_SOURCE` works as in the app: `synthetic` uses generated data, `study` needs the study file and R, `auto` (default) uses the study file if it finds one and synthetic data otherwise. On synthetic data, sections that need columns the generator doesn't produce (temperature, sleep stages) say so and skip. After editing, write changes back with `jupytext --to py:percent notebooks/<name>.ipynb` and commit only the `.py`.

## Using your own data

Any CSV or `.csv.gz` with one row per participant-day works:

```bash
HE_DATA_SOURCE=synthetic HE_SYNTHETIC_FILE=/path/to/your.csv.gz python app.py
```

Required columns: `name`, `days_since_start`, `valid80`, `class_5_min`, `average_hrv`, `average_heart_rate`, `steps`, `spo2`, `sex`. Optional columns (MET, clinical baseline fields) each switch on part of the dashboard; see [docs/synthetic-data.md → Format](docs/synthetic-data.md#format). The app runs on `127.0.0.1` with no login, so **don't load identifiable data**.

For an R `.rds` file in the study's format, install R with the `haven` package and put the single `.rds` file in a `de-identified data` folder next to the repo (or set `HE_DATA_FILE`). The app converts it once to a CSV cache outside the repo.

## How the public demo is hosted

| Piece | Where | How it updates |
|---|---|---|
| Dashboard | [Render](https://render.com) free plan, Docker, `HE_PUBLIC_DEMO=1` ([render.yaml](render.yaml)) | Manual deploy from `main` |
| Read-only notebooks | Rendered on synthetic data while the Docker image builds, served by the dashboard | With each deploy |
| JupyterLite | GitHub Pages, built by [a workflow](.github/workflows/jupyterlite.yml) from `lite/` | Every push to `main` |
| Binder | [mybinder.org](https://mybinder.org) from `binder/` | On first launch after a change |

Demo mode always uses an in-memory synthetic cohort and refuses to start if pointed at study data. Visitors' code never runs on the dashboard server: notebooks run in the visitor's browser (JupyterLite) or on Binder. Details: [docs/hosting.md](docs/hosting.md).

## Testing

```bash
python -m pytest -q
```

59 tests, about 30 s. They always run on synthetic data and never need study data, R or a network (EHR calls are mocked). They cover the generator, the measures, every page and API route, exports, the SMART launch, Medplum seeding, demo mode, and both notebooks running end to end.

## Data-safety rules

- **The study data never goes in this repo.** `.gitignore` blocks data files, `.ipynb` copies, images and PDFs as a backstop; still run `git status` before every commit.
- **Local only, no login.** Outside demo mode the app binds to `127.0.0.1` and must never be deployed with study data.
- Exported notebooks and PDF reports can contain data; don't commit them.
- Never seed an EHR from study data or map real MRNs to study IDs before IRB approval and authentication.
- A hosted copy may only run `HE_PUBLIC_DEMO=1` from this public repo ([checklist](docs/hosting.md)).

## Limitations

- **Proxies, not sleep.** Night rest, rest midpoint and regularity come from Oura's activity classes, not sleep staging, and haven't been validated against polysomnography.
- **Baseline-only clinical data, no dates or events.** Group comparisons show baseline differences, not change after an event.
- **Exploratory statistics:** unadjusted, no correction for multiple comparisons or confounding.
- **Synthetic data** only encodes the generator's assumptions ([limitations](docs/synthetic-data.md#limitations)).
- **No authentication;** the SMART launch is a proof of concept not yet tested end to end against a live EHR.

## Roadmap

1. Clinician-provided event table → before/after-event views.
2. Clinicians prioritise the measures; trim the profile to match.
3. Load data through **JupyterHealth Exchange** and launch from a production EHR via SMART on FHIR.
4. Authentication before any deployment with real data.

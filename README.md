# HE Clinician Dashboard

[![Binder](https://mybinder.org/badge_logo.svg)](https://mybinder.org/v2/gh/dicristea/ehr-wearable-he-dashboard/main?urlpath=lab/tree/notebooks)

A simpler, clinician-facing dashboard for a hepatic encephalopathy (HE) study in which patients with cirrhosis wear an Oura ring, built at Cornell Tech with JupyterHealth.

Patients with cirrhosis in the study wear an Oura ring. This app turns the ring's daily export into views a clinician can read in a few minutes: who looks worse than usual this week, what one patient's rest and activity look like over time, and how groups of patients (for example compensated vs. decompensated) compare. It was designed together with the study's clinician, a hepatologist at Weill Cornell Medicine, and it shows only what the study data actually contains (no sleep stages, no labs, no event dates).

It's a slimmed-down companion to the research prototype [oura-clinical-workbench](https://github.com/dicristea/oura-clinical-workbench). The workbench stays as is, with its ML lab, SHAP and AI assistant.

> **The public version runs on synthetic data only.** Every patient you see after following the quickstart is generated by code (`DEMO-01`, `DEMO-02`, …). Findings on synthetic data are artefacts of the generator's settings, not clinical results ([docs/synthetic-data.md](docs/synthetic-data.md)). The study data is never in this repository.

## Feature tour

| Tab | What it shows |
|---|---|
| **Patients** (`/`) | Sortable patient list with filters (patient ID, HE status, Child-Pugh, decompensated, ascites, HE meds, etiology, sex, age and MELD ranges, minimum valid days, *needs attention*). Filters apply together with **Apply filters**, and the summary bar then describes the filtered cohort. *Needs attention* = last 7 days worse than the patient's own 10–90% range on any profile measure. **Open as cohort →** sends the filtered patients to the Cohort tab. Click a patient for their profile, modelled on a Medplum patient dashboard demo: a header with a synthetic badge, a summary row (night rest, regularity, midpoint, ring wear coverage), measure cards (last 7 days vs. the patient's own usual range, with trend), a 24-hour MET activity profile, time in activity classes, a 1/3/7-day MET activity explorer, and a rest/activity actogram. |
| **Cohort** (`/cohort`) | All patients, or the selection sent from the Patients tab. Compare groups (this selection vs. the rest of the cohort, decompensation, covert or overt HE, Child-Pugh, HE meds, ascites, sex) on any measure: weekly trajectories plus one dot per patient, with a Mann-Whitney test. **Export ▾**: a PDF report of every measure (print → Save as PDF), a new pre-filled notebook that opens in JupyterLab (local only), or the same notebook as a download (`.ipynb`, stores the filters, not patient IDs). The public demo adds **Open in browser (JupyterLite)**; its notebook runs on synthetic data in a clone, Binder or JupyterLite ([docs/hosting.md](docs/hosting.md#notebook-export-in-the-demo)). |
| **Notebooks** (`/notebooks`) | The exploratory Jupyter notebooks behind the dashboard, opened in JupyterLab (with Jupyter AI if installed). In the public demo: a read-only copy run on synthetic data, or run them yourself in the browser (JupyterLite) or on Binder. |
| **EHR launch** (`/ehr`) | Bare-bones SMART on FHIR launch: an EHR (for example Medplum) opens the app on the patient in context, and we match by MRN. Includes a *Simulate launch* tester. Synthetic MRNs only. Walkthrough: [docs/medplum.md](docs/medplum.md). |

## Quickstart

Needs Python 3 and Git. Tested with Python 3.13 on macOS. <!-- TODO: confirm the minimum supported Python version and test on Linux/Windows. -->
No study data and no R are needed.

```bash
git clone https://github.com/dicristea/ehr-wearable-he-dashboard.git && cd ehr-wearable-he-dashboard
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/generate_synthetic_data.py
HE_DATA_SOURCE=synthetic python app.py
```

Open <http://127.0.0.1:5050>. You should see 24 synthetic patients (`DEMO-01` … `DEMO-24`) and an amber "synthetic demo data" banner. Stop the server with Ctrl+C.

- `generate_synthetic_data.py` writes `synthetic_data/synthetic_he.csv.gz` (24 participants, 90–180 days each, seed 7) plus a `.settings.json` with everything needed to regenerate it. `synthetic_data/` is git-ignored.
- `HE_DATA_SOURCE=synthetic` makes the app read that file and nothing else. (Without it the app uses the study file if it finds one next to the repo, and otherwise builds the same 24-patient cohort in memory.)
- `pip install -r requirements.txt` also installs JupyterLab and scikit-learn for the notebooks. The web app alone needs only `flask pandas numpy scipy nbformat` (the `Dockerfile` installs just these).
- On Windows, activate with `.venv\Scripts\activate` and set the variable with `set HE_DATA_SOURCE=synthetic` (cmd) or `$env:HE_DATA_SOURCE="synthetic"` (PowerShell). <!-- TODO: not tested on Windows. -->

Bigger or different cohorts: `python scripts/generate_synthetic_data.py --participants 40 --min-days 90 --max-days 180 --seed 7` (all options in [docs/synthetic-data.md](docs/synthetic-data.md)).

### Data flow

```
 study .rds (outside repo) ──Rscript + haven──▶ CSV cache <stem>.v2.csv (outside repo) ─┐
 synthetic CSV (HE_SYNTHETIC_FILE) ─────────────────────────────────────────────────────┼─▶ data.load()
 data.synthetic_cohort() in memory (no file / public demo) ─────────────────────────────┘      │
                                                                                                ▼
                    daily table + derived columns: night_rest_h, rest_mid_6pm, sri, grp_*  (lru_cache)
                                                                                                │
        patient_list() · patient_detail() · intraday() · cohort_summary() · cohort_compare()   │
                                                                                                ▼
                         app.py routes → Jinja templates / JSON → static/charts.js in the browser
```

1. **Source selection** (`data.load()`, controlled by `HE_DATA_SOURCE` and `HE_PUBLIC_DEMO`):

   | Mode | Reads |
   |---|---|
   | `HE_PUBLIC_DEMO=1` | always the in-memory cohort `synthetic_cohort()` (24 patients, seed 7). Refuses to start with `HE_DATA_SOURCE=study` or `HE_MRN_MAP` |
   | `HE_DATA_SOURCE=synthetic` | `HE_SYNTHETIC_FILE` (error if missing) |
   | `HE_DATA_SOURCE=study` | `HE_DATA_FILE` (error if missing) |
   | `HE_DATA_SOURCE=auto` (default) | `HE_DATA_FILE` if it exists, otherwise the in-memory synthetic cohort |

2. **Raw file → cache** (study data only). Python's `pyreadr` can't parse the `.rds` file's haven-labelled and list columns, so `data._read_rds` writes a small R script (`R_TO_CSV` in `data.py`) to `HE_CACHE_DIR` and runs `Rscript` once. It converts labelled columns to factors, drops list columns, and turns per-minute MET (`met_val`, 1,440 values per day) into 288 five-minute means (`met_5min`, comma-separated, aligned with `class_5_min`). The CSV `<stem>.v2.csv` is reused until the `.rds` is newer. The cache sits outside the repo by default so a converted copy can't be committed by accident.
3. **Derived measures** are added to every row in `load()` (next section), then the table is cached in memory (`functools.lru_cache`). **Restart the app after the data changes.**
4. **Page payloads**: `patient_list()` (Patients tab, also cached), `patient_detail()` (profile), `intraday()` (MET explorer, `/api/patient/<id>/intraday`), `cohort_summary()` and `cohort_compare()` (Cohort tab, `/api/cohort`, PDF report).
5. **Cohort selections** travel as the Patients-tab filter parameters (defined in `data.FILTERS`, parsed by `data.parse_filters`), never as lists of patient IDs. Exported notebooks store the filters too, and re-select patients when run.

## How the measures are computed

All of this is in `data.py`. The input is one row per participant-day. Oura's `class_5_min` is a 288-character string, one character per 5-minute slot of a day that runs **04:00 → 04:00** local: `0` ring off, `1` rest, `2` inactive, `3` low, `4` medium, `5` high activity. A string with the wrong length or other characters is treated as missing. The file has no sleep stages, so the three sleep measures are **proxies** built from the rest class.

| Measure | How it's computed |
|---|---|
| **Valid day** | `valid80 == 1` (ring worn ≥ 80% of the day; the synthetic generator sets it when `non_wear_pct ≤ 0.2`). Every per-patient and cohort summary uses valid days only. |
| **Night rest** (`night_rest_h`, hours) | Join day *d* and day *d+1*, take the window **18:00 on day *d* → 12:00 on day *d+1*** (18 h). Find rest bouts: runs that start and end with a rest slot, where gaps of at most 2 non-rest slots (≤ 10 minutes, any class including ring off) are bridged. Take the longest (the first one on a tie). Bouts under 2 h, and any value outside 2–16 h, are missing. Computed only when days *d* and *d+1* are consecutive study days, both are valid and both strings are well formed. Stored on day *d*. |
| **Rest midpoint** (`rest_mid_6pm`) | Middle of that same bout, in hours after 18:00; shown as clock time (e.g. `03:15`). Has no "better" direction. |
| **Rest regularity** (`sri`, −100 to 100) | Adapted from the Sleep Regularity Index. Compare day *d* and day *d+1* slot by slot at the same clock time, using only slots where the ring was on (class ≠ 0) on both days. Needs at least 80% of the 288 slots. SRI = 200 × (share of those slots where both days agree on rest vs. not rest) − 100. 100 = identical days, 0 = the days agree on half the slots. Needs consecutive days with well-formed strings; stored on day *d*, and summaries then keep only valid days *d*. |
| **HRV, average HR, steps, SpO₂** | Taken from the file (`average_hrv`, `average_heart_rate`, `steps`, `spo2`). `average_heart_rate == 0` is a device error and becomes missing. |
| **MET** | Study data: per-minute MET → five-minute means (see Architecture). The **24-hour activity profile** shows, for each 5-minute slot, the 10th/25th/50th/75th/90th percentile of MET across the patient's valid days, plus the share of valid days the slot was rest. **Time in activity classes** is the share of slots per class and the average hours per day, over valid days. The **activity explorer** shows raw 5-minute MET and class for 1, 3 or 7 consecutive days. |
| **Measure cards** (profile) | For each measure in `data.PATIENT_TILES`: *last 7* = median of the patient's last 7 valid-day values (the last 7 non-missing values, not the last 7 calendar days); *usual range* = the patient's own 25th–75th percentile over all valid days; status = below / typical / above. **Trend** (needs ≥ 28 values): median of the last 14 values vs. the 28 before; the difference divided by the usual-range width (IQR) above +0.5 is *Increasing*, below −0.5 *Decreasing*, otherwise *Stable*. |
| **Needs attention** (Patients tab) | For each measure in `PATIENT_TILES` with at least 14 valid-day values: flag it when the median of the last 7 values is outside the patient's own **10th–90th percentile** in the worse direction (lower is worse for night rest, regularity, HRV, steps and SpO₂; higher is worse for heart rate; rest midpoint never flags). Stricter than the cards' 25–75% range so ordinary weeks don't trigger it. A patient needs attention if any measure is flagged. |
| **Ring wear coverage** (profile) | Share of study days 1…last day that are valid (days missing from the file count as not valid), plus the median daily wear `1 − non_wear_pct`. The Patients-tab "valid days %" and the valid-days filter use the share of rows in the file instead. |
| **HE status** | `Overt` if `anyOHE == 1`, else `Covert` if `che_phes == "Yes"`, else `No` if `anyhe == 0`, otherwise unknown. Clinical fields are baseline only (first row per patient). |
| **Patient-list values** | Medians over valid days. The sparkline is the 7-day rolling mean of night rest (at least 3 values), every third day. |
| **Cohort summary** | Night rest and regularity are the median of per-patient medians, so each patient counts once. |
| **Cohort comparison** | Valid days only. **Trajectory**: each patient's mean per study week (week = (day − 1) // 7 + 1), then the median and 25th–75th percentile across patients, for weeks with ≥ 5 patients in the group. **Dots**: each patient's median across valid days. **Test**: two-sided Mann-Whitney U on those per-patient medians (`scipy.stats.mannwhitneyu`) when both groups have ≥ 3 patients; effect size r = 1 − 2U / (n₁·n₂) (rank-biserial). Exploratory and unadjusted. |

## Using your own data

Any CSV or `.csv.gz` with one row per participant-day works:

```bash
HE_DATA_SOURCE=synthetic HE_SYNTHETIC_FILE=/path/to/your.csv.gz python app.py
```

Required columns: `name`, `days_since_start`, `valid80`, `class_5_min`, `average_hrv`, `average_heart_rate`, `steps`, `spo2`, `sex`. Optional columns (MET, clinical baseline fields) each switch on part of the dashboard. The full schema, valid values and caveats are in [docs/synthetic-data.md → Format](docs/synthetic-data.md#format) and [Using your own dataset](docs/synthetic-data.md#using-your-own-dataset).

The app labels data loaded this way as synthetic (amber banner, generated MRNs), runs on `127.0.0.1` and has no login: **don't load identifiable data**.

To use an R `.rds` file in the study's format instead, install R with the `haven` package (`Rscript -e 'install.packages("haven")'`), then run `HE_DATA_SOURCE=study HE_DATA_FILE=/path/to/file.rds python app.py`. Without `HE_DATA_FILE`, the app looks for the single `.rds` file in a `de-identified data` folder next to the repo:

```
JupyterHealth/
├── de-identified data/
│   └── <your study file>.rds                           ← local only, never in the repo
├── exploration_outputs/_cache/                         ← auto-created CSV cache (local only)
└── ehr-wearable-he-dashboard/                         ← this repo
```

## Synthetic data

`data.synthetic_cohort()` generates a cohort in the study file's format: per-participant baseline fields, per-day activity strings, MET, HRV, heart rate, steps and SpO₂. Every assumption is a setting in `data.SYNTHETIC_DEFAULTS`, and any of them can be overridden with a JSON file (`--config`). The same seed and settings always give an identical file.

The only built-in link between clinical status and the wearable data is **decompensation** (shorter, later, less regular rest; lower HRV; higher heart rate; fewer steps). Anything the dashboard shows beyond that is noise. Details, every setting, and limitations: [docs/synthetic-data.md](docs/synthetic-data.md).

## EHR launch (SMART on FHIR) and Medplum

The **EHR launch** tab is a minimal SMART on FHIR EHR launch (authorization code with PKCE). The EHR opens `/ehr/launch?iss=…&launch=…`, the app reads `/.well-known/smart-configuration`, redirects to the EHR's authorize endpoint, exchanges the code at `/ehr/callback`, reads the launched FHIR `Patient`, takes its identifier under `SMART_MRN_SYSTEM`, and opens that patient's profile. Wearable data never goes into the EHR.

- Synthetic patients get a fixed MRN: `DEMO-07` → `JH-DEMO07` (`data.synthetic_mrn`). *Simulate launch* tests the matching without any EHR.
- `scripts/seed_medplum.py` creates a FHIR `Patient` for every synthetic patient in a Medplum project (`--dry-run` prints the transaction Bundle without network calls). It refuses any ID that isn't `DEMO-<n>`.
- Study data has no MRNs. A real mapping (`HE_MRN_MAP`) is only for after IRB approval and authentication.

Step-by-step setup, compatibility notes (what was and wasn't verified against a live Medplum project) and troubleshooting: [docs/medplum.md](docs/medplum.md).

## Public demo and hosting

`HE_PUBLIC_DEMO=1` turns the app into a public demo: always the in-memory synthetic cohort, never any data file; writing notebooks to disk, the Notebooks file list and the real SMART launch routes are off (notebook download and JupyterLite stay on); `X-Robots-Tag: noindex` on every response; Flask debugger off; may bind beyond `127.0.0.1` (`HOST`). Try it locally:

```bash
HE_PUBLIC_DEMO=1 python app.py                                         # http://127.0.0.1:5050
docker build -t he-demo . && docker run --rm -p 127.0.0.1:8000:8000 he-demo   # http://127.0.0.1:8000
```

The `Dockerfile` has two stages: a builder that runs both notebooks on synthetic data and exports read-only HTML (`scripts/render_notebooks.py`), and the runtime, which copies only `app.py`, `data.py`, `templates/`, `static/` and that HTML and runs gunicorn with `HE_PUBLIC_DEMO=1` forced in the start command. `render.yaml` describes one free Render web service. Nothing has been deployed. The full comparison table, deployment steps and the pre-publication checklist are in [docs/hosting.md](docs/hosting.md); the first deploy, click by click, is in [docs/render-quickstart.md](docs/render-quickstart.md).

## Notebooks

Notebooks are committed only as [jupytext](https://jupytext.readthedocs.io) percent-format `.py` files, with no outputs. Runnable `.ipynb` copies are git-ignored because their outputs can contain data.

| Notebook | What it does |
|---|---|
| `notebooks/deid_oura_data_exploration.py` | Beginner-friendly tour of the de-identified dataset: who is in it, completeness, sleep proxies, what exists vs. the research workbench. Reads `JH_DATA_DIR`. |
| `notebooks/he_trajectories_phenotypes.py` | Group trajectories and individual phenotypes (clustering), and why pre/post-event analysis isn't possible with the current file. Reads `JH_DATA_FILE`. |

Both use the app's `HE_DATA_SOURCE` switch, set before starting Jupyter: `auto` (default) reads the study data when it finds it (exactly one `.rds` in `../de-identified data/`, or `JH_DATA_DIR` / `JH_DATA_FILE` set) and otherwise the synthetic cohort; `study` needs the study file and R; `synthetic` needs neither. On synthetic data the table comes from `data.py` (`HE_SYNTHETIC_FILE` if it exists, otherwise the default in-memory cohort the public demo shows), summary tables are saved to the git-ignored `notebook_outputs/`, and sections that need columns the synthetic cohort lacks (temperature, sleep stages) say so and skip. **On synthetic data every result, p-values, phenotypes and correlations included, is an artefact of the [generator settings](docs/synthetic-data.md), not a clinical finding.**

### Run the notebooks online (synthetic data)

Without installing anything, from the hosted demo's **Notebooks** tab or directly:

- **Binder**: [launch JupyterLab](https://mybinder.org/v2/gh/dicristea/ehr-wearable-he-dashboard/main?urlpath=lab/tree/notebooks) on free cloud servers; the first start after a change can take a few minutes. `binder/` installs only the notebook stack, generates the default synthetic cohort and converts the `.py` files to blank `.ipynb` (`postBuild`), and sets `HE_DATA_SOURCE=synthetic` (`start`).
- **JupyterLite**: [the same notebooks running in your browser](https://dicristea.github.io/ehr-wearable-he-dashboard/lab/index.html?path=notebooks/he_trajectories_phenotypes.ipynb) with Pyodide; nothing runs on a server. GitHub Pages builds it from `lite/` on every push to `main` (first visit downloads about 100 MB; [docs/jupyterlite.md](docs/jupyterlite.md)).

Both use only generated data; results are generator artefacts, not clinical findings ([docs/synthetic-data.md](docs/synthetic-data.md)).

### Run them locally

```bash
jupytext --to ipynb notebooks/*.py     # make runnable copies (ignored by git)
HE_DATA_SOURCE=synthetic jupytext --to ipynb --execute notebooks/*.py   # or run them end to end on synthetic data
jupyter lab --port 8888                # start from the repo folder so the dashboard's links work
```

Workflow: edit the `.ipynb` in JupyterLab, then write the changes back with `jupytext --to py:percent notebooks/<name>.ipynb` (the `.py` keeps code and markdown, never outputs; jupytext may also expand the header metadata, which is harmless). Only commit the `.py`. The dashboard's Notebooks tab lists `.ipynb` files in `NOTEBOOK_DIRS` and links them to JupyterLab at `JUPYTER_BASE_URL`; **Cohort → Export → New notebook** writes a pre-filled notebook there that stores the cohort's filters, not patient IDs; **Download notebook** returns the same file without writing it.

## Data-safety rules

- **The study data is never in this repo.** It stays outside the repo folder. `.gitignore` blocks `.rds`, `.csv*`, `.parquet`, `.ipynb`, images, PDFs, `exploration_outputs/`, `synthetic_data/` and similar files as a backstop. Run `git status` before every commit.
- **Local only.** With anything but the public demo, the app binds to `127.0.0.1`, has **no login**, and must never be deployed with study data.
- Notebooks are committed only as blank jupytext `.py` files. `.ipynb` copies, exported notebooks and PDF reports can contain data.
- Never seed an EHR from study data, and never map real MRNs to study IDs until IRB approval and authentication are in place.
- A hosted copy may only run `HE_PUBLIC_DEMO=1` from the public repo; follow the checklist in [docs/hosting.md](docs/hosting.md).

## Limitations

- **Proxies, not sleep.** Night rest, rest midpoint and regularity come from Oura's activity classes, not sleep staging, and no validation against polysomnography or Oura's own sleep summaries is documented here. <!-- TODO: add validation status if any exists. -->
- **Baseline-only clinical data, no calendar dates, no event dates.** Group comparisons describe baseline differences, not change after an event; pre/post-event views need an event table (see the trajectories notebook).
- **Exploratory statistics.** Mann-Whitney tests are unadjusted, uncorrected for multiple comparisons and for confounding.
- **Synthetic data** encodes the generator's assumptions only ([limitations](docs/synthetic-data.md#limitations)).
- **No authentication**; the SMART launch is a proof of concept not yet tested end to end against a live EHR ([docs/medplum.md](docs/medplum.md)).
- Data is cached in memory; restart after the data file changes.

## Roadmap

1. Clinician-provided event table (`name`, `study_day`, `event_type`) → pre/post-event views.
2. Clinicians prioritise the measures in a follow-on study, then trim the tiles to match.
3. Swap the local loader for **JupyterHealth Exchange** (`jupyterhealth-client`) and add a **SMART on FHIR** launch from a production EHR, matching patients by MRN.
4. Add authentication before any deployment.
